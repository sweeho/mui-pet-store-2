# Design — Bootstrap, landing page and shared site shell

## Context

This change is generated by the platform for every migration and greenfield initiative (architecture doc 41). The capability brief canvas, its wireframes and its mockups are the detailed design; this document records the decisions every other capability relies on.

## Decisions

Each decision below is an architecture decision record (ADR) with its reason and the options rejected. Each is also listed under `## Key Decisions` in the project `ARCHITECTURE.md`, by the same ID (D1 to D5), so the next person or agent finds the reason before changing it.

- **D1. One shell.** Every page renders inside the same layout, header, navigation and footer. A capability adds content to the shell; it never draws its own chrome.
  - Reason: one place to change chrome, a consistent look, and one set of accessibility behaviour (skip link, landmarks, focus order) to keep correct.
  - Rejected: (a) a layout per capability, because chrome drifts and every capability repeats the accessibility work; (b) a shell for most pages with opt-out pages, because exceptions grow and the shell stops being a guarantee.
  - Limits later work: a capability needing a full-screen or chrome-free page must first change the shell, not work around it.

- **D2. One navigation.** The global navigation lists every primary area and always links back to the landing page. A capability that adds a primary area adds one entry here rather than a second menu.
  - Reason: a user always has one place to find every area and a way home.
  - Rejected: (a) a menu per capability, because users meet several menus and a way home is not guaranteed; (b) a navigation built only from the current page's links, because areas become unreachable from elsewhere.
  - Limits later work: a new primary area edits the one list in `src/shell/SidebarItems.tsx` (`MENU_ITEMS`).

- **D3. Shared states.** Empty, error and loading frames are components of the shell, reused by every page.
  - Reason: users see the same wording and behaviour for the same condition, and each fix is made once.
  - Rejected: (a) each page building its own states, because they diverge and are tested many times over; (b) states only at route level (`loading.tsx`, `error.tsx`), because they cannot cover a region of a page.
  - Limits later work: a page needing a different state changes the shared component for everyone.

- **D4. Existing boilerplate wins.** Where the repository already has an application scaffold, extend it rather than scaffold again.
  - Reason: a second scaffold duplicates configuration, build and test setup, and divides the codebase in two.
  - Rejected: (a) scaffolding afresh beside the existing one, because two stacks must be kept in step; (b) replacing the existing scaffold, because it discards working, pinned and tested setup for no product gain.
  - Limits later work: stack and structure follow the scaffold already in the repository (the Next.js, MUI and Modernize shell in `src/shell/`).

- **D5. Sign-in only if the product has it.** The shell carries a sign-in frame only when the product requirements call for authentication.
  - Reason: a sign-in frame with no authentication behind it misleads users and is dead code to maintain.
  - Rejected: (a) always including a sign-in frame, because it implies access control that does not exist; (b) adding it later per page, because it would break D1 by drawing chrome outside the shell.
  - Limits later work: adding authentication later adds the frame to the shell once, under D1.

## Codebase findings (sprint planning, SWHM3-S-0001)

Read at the sprint branch head (`19a26c1`):

- `src/app/(DashboardLayout)/layout.tsx` wraps every page in `DashboardShell` (`src/shell/DashboardShell.tsx`): `Sidebar` (permanent `Drawer` at `lg` and up, temporary drawer below), `Header` (MUI `AppBar`, renders `<header>`, so a `banner` landmark) and `<Box component="main">`. **There is no footer** and so no `contentinfo` landmark.
- `src/shell/SidebarItems.tsx`: `MENU_ITEMS = [{ title: "Home", href: "/" }]`, rendered in a `List component="nav"`; the store name (`APP_NAME`, `src/constants/app.ts`) links to `/` but sits outside the `<nav>`. Selection is exact-match (`pathname === item.href`).
- `src/shell/Sidebar.tsx`: `SIDEBAR_WIDTH = "270px"`, hard-coded scrollbar colour `#eff2f7`.
- `src/app/(DashboardLayout)/page.tsx` is `force-dynamic`, reads `findUser(1)` and renders `HomeView` ("Hello, world" + first demo user). `e2e/home.spec.ts`, `e2e/smoke.spec.ts` and `src/components/HomeView.test.tsx` assert that placeholder.
- `src/app/not-found.tsx` sits outside the route group, so a 404 renders **without** the shell. There is no `error.tsx`, `loading.tsx` or shared state component anywhere.
- `design/tokens.mui.json` holds Modernize Free values (`#5D87FF`, Plus Jakarta Sans, radius 7); the approved mockups use the Design Reference (`#4f46e5`, Inter, radius 4, text `#0f172a`, muted `#64748b`, divider `#e2e8f0`, paper `#f8fafc`, success `#16a34a`, warning `#d97706`, error `#dc2626`, info `#0284c7`). The font is imported in `src/app/layout.tsx` from `@fontsource-variable/plus-jakarta-sans` (pinned in `package.json`).
- The locked acceptance spec `tests/acceptance/site-shell/e2e/site-shell.spec.ts` (cases C-0163..C-0167) defines what "done" is mechanically:
  - the landing page's links inside `main` must include every non-root link in the first `navigation` landmark, and there must be at least two;
  - every linked page must show `banner`, `navigation`, `main` and `contentinfo`, and the first `navigation` must hold a link to `/`;
  - C-0166 and C-0167 only judge linked pages that make a **browser request to a path containing `/api/`**, and fail when none does. With every `/api/**` answered `[]` the page shows empty wording (for example "No languages available") and no retry button; with `500` it shows a `role="alert"` or "couldn't load" message and a button named exactly **Try again**, whose click re-requests `/api/...` from the browser and clears the error.
- CI (`.github/workflows/ci.yml`) already runs on pull requests to `vortex/**`, `dev` and `main` and runs the acceptance suites (non-gating until green). No CI change is needed.
- Other capabilities' locked tests use `/admin`, `/admin/orders`, `/locale` and `/api/locale`. This change must not take those paths over with anything they would collide with.

## Implementation decisions for this sprint

- **P1. Primary areas and routes.** The rail carries Home (`/`) plus the proposal's two areas, in one group: Localization at `/localization` and Order administration at `/admin/orders`. `MENU_ITEMS` stays the single list (D2). The landing page's cards are generated from the same list, so the landing page and the rail cannot drift apart. The store name and the Home entry both link to `/`, and the Home entry sits inside the `<nav>`.
- **P2. Area placeholders.** Until their capabilities ship, both area routes are placeholder pages inside the shell. `/admin/orders` shows the shared empty frame ("No orders yet"). The order-administration capability replaces that page.
- **P3. One data-loading page now (needed by C-0166/C-0167).** `/localization` loads the supported languages from the browser through a new public, read-only `GET /api/locales` route (a constant list in `src/lib/locales.ts`, no database, no personal data). It renders through one shared client hook/component that picks the loading, error (Try again re-runs the fetch) or empty frame, or the data. That gives the shared frames a real consumer and the locked specs a page to judge. The route does not touch `/api/locale`, which belongs to localization.
- **P4. Frames.** `src/components/StateFrames/` exports `EmptyState`, `ErrorState` and `LoadingState`. `ErrorState` uses `role="alert"`, a "We couldn't load …" title, a **Try again** button and an optional "Go to home" link, and logs the error (OBS-003). `(DashboardLayout)/error.tsx` and `loading.tsx` reuse them. A catch-all `(DashboardLayout)/[...missing]/page.tsx` calls `notFound()`, so a 404 renders inside the shell.
- **P5. Look.** Replace `design/tokens.mui.json` with the Design Reference tokens and swap the font package for `@fontsource-variable/inter` (OFL-1.1, checked against CMP-001). The rail becomes 240px with a theme-driven scrollbar colour. No colour is written in a component.
- **P6. Out of this sprint** (brief's Out of Scope): the header's sign-in button, the language selector and the Shop/Admin grouping with catalog, cart and similar entries shown in the mockups. The rail must stay the **first** `navigation` landmark in the DOM, so add no breadcrumbs `<nav>` ahead of it.

## Phases

1. **Look**: tokens, the Inter font, the rail width (P5).
2. **Shell**: footer, primary-area entries in `MENU_ITEMS`, prefix-match highlighting, the 404 inside the shell (P1, P4).
3. **Landing page**: replace `HomeView` with `LandingView`, generated from `MENU_ITEMS` (P1).
4. **Shared frames and placeholders**: the three frames, `error.tsx`/`loading.tsx`, the resource hook, `/api/locales`, and the two area pages (P2 to P4).
5. **Test harness**: jsdom tests beside each new component and the `/api/locales` route test; rewrite `e2e/home.spec.ts` for the landing page and rail; keep `e2e/smoke.spec.ts` loading the root route with an h1 and no console errors; an automated WCAG 2.2 AA check of the landing page and each frame (A11Y-001). The locked acceptance spec stays untouched and must pass.
6. **CI**: no workflow change. The existing workflow already triggers on pull requests to `vortex/**` and runs the unit, E2E and acceptance suites. This change is done when those jobs are green on the ticket's pull request.

## Spec discrepancies

- **SD1. "No API routes change" (canvas, Affected Code) and the locked cases C-0166/C-0167.** The locked specs only exercise a primary-area page that issues a browser `/api/` request, and fail when none does. A shell made only of static placeholders cannot pass them. Resolved by P3, a public read-only `GET /api/locales`. The delta spec is unchanged.
- **SD2. Primary areas.** The proposal and delta spec name Localization and Order administration. The approved mockups draw a Shop/Admin rail with Catalog, Search, Cart, Sign in, Profile, Language, Orders, Sales charts and Inventory, plus a header with a sign-in button and a language selector. This sprint builds to the spec (two areas) and the brief's Out of Scope. Each later capability adds its own entry (D2). The open question of which areas belong in the rail stays open.
- **SD3. Localization as a destination.** The brief notes Localization is a language switcher rather than an area. `/localization` is a placeholder destination, the supported-languages page, until the localization capability decides whether it becomes a control.
- **SD4. The 404 sits outside the shell today.** The brief's success metric requires every page, including "page not found", to be in the shell. Delta spec R-0228 says "every page" without naming the 404. Covered by P4.
